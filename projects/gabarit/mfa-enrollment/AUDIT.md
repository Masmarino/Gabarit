# RGAA Audit — MfaEnrollment

Checked against RGAA 4.1.2 by the unit tests (`mfa-enrollment.spec.ts`, jsdom, including axe-core
runs through `expectNoA11yViolations`), by the play functions of `Auth/MfaEnrollment` in Storybook
(stories `Intro`, `IntroError`, `Scan`, `ScanError`, `Codes`, `CodesAcknowledged`, `Choice`,
`ChoiceError`, `PasskeyName`, `PasskeyBusy`, `PasskeyError`, `PasskeyCancelled`,
`PasskeyAlreadyRegistered`, `PasskeyCodes`, `Dark`, `Phone`, `Localised`), and by code review
(`mfa-enrollment.ts`, `mfa-enrollment.html`, `mfa-enrollment.scss`). The stories are type-checked but
not run in this environment: the rows that rely on them say so.

axe-core (WCAG 2.0/2.1/2.2 A and AA rules, contrast excluded) reports no violation on: the
introduction, the introduction with an error, the choice, the scan step (with the QR, and with a
refused code), the passkey step (the name field, the prompt open, an error, the quiet "cancelled"
note) and the backup codes.

A `beforeunload` guard warns the user before they navigate away from the `codes` step while its

## Externalized strings

Every string of the component is a member of `MfaEnrollmentLabels`, with its English default in
`DEFAULT_MFA_ENROLLMENT_LABELS` (including the step counter, `step(current, total)`, the backup-code
lead, `codesLead(factor)`, the default passkey name, which is also the field's placeholder, and every
failure message). They are changed by the `labels` input and, application-wide, by
`provideAuthLabels({ mfaEnrollment })`; the input wins, string by string. The nested `gbt-totp-qr` and
`gbt-backup-codes` take theirs from `provideAuthLabels({ totpQr, backupCodes })`.

Verified by the spec: the `labels` input changes the step counter, the heading, the primary button and
a failure message, the rest keeping its English default; `provideAuthLabels` changes the component's
strings and those of the nested QR and backup codes; the `labels` input wins over `provideAuthLabels`.
The `Localised` story shows the whole component in French.
