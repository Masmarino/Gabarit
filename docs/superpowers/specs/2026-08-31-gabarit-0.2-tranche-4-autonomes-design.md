# Gabarit 0.2 — Tranche 4 : les quatre graphiques autonomes — Design

## Contexte

Trois tranches ont bâti la couche : douze primitives pures, le socle
`gbt-chart-frame` et ses cinq briques, puis les trois graphiques cartésiens.

La tranche 4 livre les quatre derniers — `gbt-sparkline`, `gbt-gauge-bar`,
`gbt-funnel-chart`, `gbt-dimension-card` —, solde trois dettes des tranches
précédentes, et **clôt la 0.2** par la montée de version.

Spec parente : [`2026-08-30-gabarit-0.2-dataviz-design.md`](./2026-08-30-gabarit-0.2-dataviz-design.md).

## Ce que la lecture du code a corrigé dans la spec parente

### Deux des quatre ne sont pas des graphiques SVG

La spec parente range les quatre autonomes ensemble : ils « consomment
directement l'étage 1 », c'est-à-dire les primitives.

C'est vrai d'un seul. `gbt-sparkline` trace une courbe, et emploie donc
`linearScale` et `linePath`.

**Les trois autres n'ont ni axe, ni échelle, ni chemin à tracer.**
`gbt-funnel-chart` empile des bandeaux à largeur proportionnelle.
`gbt-gauge-bar` est une barre de remplissage — `width: 62%` sur un `div`
suffit, et c'est déjà ainsi qu'il est écrit dans l'application Hangar, où il
sert à trois endroits. `gbt-dimension-card` est une table dont chaque ligne
porte une barre de proportion en fond.

**Décision : `gbt-sparkline` seul en SVG, les trois autres en HTML et CSS.**

Une courbe est un chemin : `gbt-sparkline` a besoin de `linePath` et d'une
échelle, et rien d'autre ne sait tracer ça.

Les trois autres sont des largeurs proportionnelles. Un `viewBox` mis à
l'échelle y coûterait cher pour rien : **il étire le texte des libellés**,
qui grandit et rétrécit avec le graphique — exactement le défaut que la spec
parente reproche au `line-chart` d'origine, « le SVG étiré déforme
l'épaisseur des traits et interdit tout texte d'axe ». En HTML, `width: 62%`
suffit et le texte garde sa taille.

L'entonnoir a d'abord été rangé du côté SVG lors du choix de conception. Le
raisonnement qui met `gbt-gauge-bar` en CSS vaut mot pour mot pour lui : des
étapes empilées à largeur proportionnelle sont de la mise en page, pas du
tracé.

### La table `sr-only` n'est pas due par les quatre

La spec parente exige qu'un graphique expose ses données en table
visuellement masquée — critère 1.1, un SVG étant invisible à un lecteur
d'écran.

Le critère demande une **alternative à l'image**, pas une table pour la
table. Or `gbt-gauge-bar` affiche déjà sa valeur en texte à côté de la
barre, et `gbt-dimension-card` _est_ une table visible. Leur en ajouter une
masquée ferait entendre deux fois la même chose et allongerait le parcours
sans rien apprendre.

**Décision : la table `sr-only` pour `gbt-sparkline` et
`gbt-funnel-chart`, dont le tracé ne dit rien à qui ne le voit pas. Pour les
deux autres, la sémantique du contenu suffit** — et pour `gbt-gauge-bar`,
elle est même plus juste qu'une table : voir plus bas.

## Les quatre composants

|                      | Rendu    | Entrée principale      | Table `sr-only`            |
| -------------------- | -------- | ---------------------- | -------------------------- |
| `gbt-sparkline`      | SVG      | `values: number[]`     | oui                        |
| `gbt-funnel-chart`   | HTML/CSS | `steps: FunnelStep[]`  | oui                        |
| `gbt-gauge-bar`      | HTML/CSS | `value`, `max`         | non — `role="progressbar"` |
| `gbt-dimension-card` | HTML/CSS | `rows: DimensionRow[]` | non — table visible        |

### `gbt-sparkline`

```typescript
values = input.required<number[]>()
label = input.required<string>() // légende de la table sr-only
xColumn = input.required<string>()
yColumn = input.required<string>()
locale = input.required<string>()
width = input(80)
height = input(24)
```

**Des valeurs nues, pas des points.** Une micro-courbe n'a pas d'axe : son
abscisse est le rang. Exiger `{ x, y }` obligerait chaque appelant à
inventer des abscisses qui ne seraient jamais affichées.

**Une taille fixe, pas mesurée.** Elle vit dans une cellule de tableau : y
poser un `ResizeObserver` par ligne coûterait cher pour une largeur que le
consommateur connaît déjà. Défauts de 80 × 24.

Le SVG porte `aria-hidden="true"` ; la table `sr-only` est le chemin non
visuel, avec une ligne par valeur et le rang en première colonne.

**C'est le seul des quatre à porter un `size` implicite**, et c'est
justifié : une courbe a besoin d'un repère en pixels pour être tracée, là où
un pourcentage se passe de toute mesure.

### `gbt-funnel-chart`

```typescript
export interface FunnelStep {
  label: string
  value: number
}

steps = input.required<FunnelStep[]>()
label = input.required<string>()
locale = input.required<string>()
emptyMessage = input.required<string>()
tableCaption = input.required<string>()
stepColumn = input.required<string>()
valueColumn = input.required<string>()
conversionColumn = input.required<string>()
```

Chaque étape est un bandeau horizontal dont la largeur, en pourcentage, est
proportionnelle à `value / steps[0].value`. Le décrochage entre deux étapes consécutives se lit
dans l'écart des largeurs, et se dit dans la table.

**La table porte trois colonnes** : l'étape, sa valeur, et son taux de
conversion depuis la première. Le décrochage se déduit de deux lignes
voisines ; l'ajouter en quatrième colonne dirait deux fois la même chose.

**Le critère 3.1 ne pose pas de problème** : chaque bandeau porte son
libellé, et la couleur ne distingue rien — c'est la position et la largeur
qui portent l'information.

L'entonnoir n'a donc **pas** d'entrée `size` : sa largeur est celle de son
conteneur, ses hauteurs sont en `rem`.

### `gbt-gauge-bar`

Le composant existe déjà dans Hangar, employé à trois endroits. On en
reprend la forme, corrigée sur trois points.

```typescript
value = input.required<number>()
max = input.required<number>()
label = input.required<string>()
/** Valeur déjà formatée — « 62 Go / 100 Go ». */
formattedValue = input.required<string>()
warningLabel = input.required<string>()
criticalLabel = input.required<string>()
thresholds = input<{ warning: number; critical: number }>({ warning: 70, critical: 90 })
```

**Les libellés de sévérité deviennent des entrées requises.** La version de
Hangar porte « Critique » et « Avertissement » en dur. Publier deux chaînes
françaises dans une librairie qui n'embarque aucun mécanisme de traduction
serait indéfendable, et un consommateur anglophone n'aurait aucun moyen de
les changer.

**`valueFormatter` devient `formattedValue`, une chaîne.** Ce projet a déjà
jugé qu'une fonction en entrée se type, se teste et se lit moins bien qu'une
donnée.

**Les seuils deviennent une entrée**, avec les valeurs de Hangar par défaut.
Ils étaient figés dans le code.

#### Pourquoi `role="progressbar"` plutôt qu'une table

```html
role="progressbar" [attr.aria-valuenow]="value()" [attr.aria-valuemin]="0"
[attr.aria-valuemax]="max()" [attr.aria-valuetext]="formattedValue()" [attr.aria-label]="label()"
```

C'est la sémantique exacte de ce qu'est ce composant. Un lecteur d'écran
annonce alors la valeur, son maximum et son texte, sans qu'on lui construise
une table à une ligne.

**Le second signal non coloré reste le libellé de sévérité**, affiché en
texte à côté de la valeur — c'est déjà ce que fait la version de Hangar, et
c'est ce qui satisfait le critère 3.1 : la couleur du remplissage ne porte
alors rien que le texte ne dise.

### `gbt-dimension-card`

```typescript
export interface DimensionRow {
  label: string
  value: number
}

rows = input.required<DimensionRow[]>()
caption = input.required<string>()
labelColumn = input.required<string>()
valueColumn = input.required<string>()
emptyMessage = input.required<string>()
locale = input.required<string>()
```

**Une vraie `<table>` visible**, pas une liste. Ces données _sont_
tabulaires — un libellé, une valeur — et une table donne gratuitement à un
lecteur d'écran la structure qu'une `<ul>` lui refuserait : en-têtes de
colonne, association cellule-en-tête, navigation par ligne.

La barre de proportion est un **fond de ligne** en CSS, dont la largeur vaut
`value / max`. Elle est décorative : l'information est déjà dans la cellule
de valeur.

## Les trois dettes des tranches précédentes

C'est la dernière tranche : ce qui n'y entre pas sort avec la 0.2.0.

### `niceXDomain` et `niceYDomain` entrent dans l'API publique

Elles ne le sont pas. Un consommateur qui assemble lui-même
`gbt-chart-frame` avec un `AxisSpec` fourni à la main obtient donc une
géométrie hors cadre sans avertissement — mesuré en tranche 3 : des barres à
378 px pour une boîte de 252.

Les exporter, et documenter le contrat : **un `AxisSpec` fourni à la main
doit avoir des bornes qui sont des graduations, et contenir zéro pour un
histogramme.**

### Le test de navigation clavier de `line-chart` ne discrimine rien

Il passerait à l'identique sur le code fautif qu'il prétend garder, et son
commentaire est factuellement faux. Le remplacer par une assertion qui
distingue réellement les deux implémentations.

### `chart-axis` éclaircit ses étiquettes de catégories

Sept catégories se chevauchent aujourd'hui à 320 px. Les axes linéaire et
temporel s'éclaircissent d'eux-mêmes, par `niceTicks` et `timeTicks` ; l'axe
de catégories affiche toutes les siennes.

**On ne peut pas mesurer du texte** — jsdom n'a pas de moteur de mise en
page, et la tranche 2 a déjà refusé une mesure qui ne fonctionnerait qu'en
navigateur. La largeur d'une étiquette est donc **estimée** à
`longueur × 6,5 px`, pour une police de 12 px, et l'on garde une étiquette
sur `k`, où `k` est le plus petit entier tel que `k × pas ≥ largeur + 8`.

Mesuré sur les cas réels :

| Cas                                            | Pas      | Plus large | Gardées |
| ---------------------------------------------- | -------- | ---------- | ------- |
| 7 catégories du tableau de bord Hangar, 320 px | 33,1 px  | ~39 px     | 4 sur 7 |
| les mêmes, 900 px                              | 120,6 px | ~39 px     | 7 sur 7 |
| 3 catégories courtes, 320 px                   | 77,3 px  | ~19,5 px   | 3 sur 3 |
| 3 libellés longs, 320 px                       | 77,3 px  | ~104 px    | 2 sur 3 |

**Ce que cette règle ne promet pas** : elle repose sur une estimation, pas
sur une mesure. Une police très large ou très étroite la mettrait en défaut.
Les catégories masquées restent toutes dans la table `sr-only` — c'est ce
qui rend l'éclaircissement acceptable.

## La montée en 0.2.0

Version du paquet, constante `GABARIT_VERSION`, README, et un tag `v0.2.0`.
C'est la dernière tâche, quand tout le reste est vert.

## Vérification

Le dispositif à quatre couches s'applique sans modification. S'ajoutent
`axe-core` sur chaque composant, un test de structure sur chaque table
`sr-only`, et un test des attributs ARIA de `gbt-gauge-bar`.

**Le reflux à 320 px se mesure au navigateur**, comme en tranche 3, avec le
contournement que cet environnement impose : le volet est masqué, donc
`requestAnimationFrame` ne tourne pas et `ResizeObserver` ne délivre rien —
**une capture d'écran force le rendu**, et toute mesure prise avant elle est
vide de sens.
